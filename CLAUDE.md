# NoyvjGames — Game Demo Hub

Personal portfolio site collecting small AI-assisted game demos. One demo, SOL, is also a dual BCM114/BCM206 university digital artefact — the site's public availability + update history is the evidence for that requirement.

## Site-level rules
- **Shared shell, free internals.** The hub (nav, title cards, review widget) stays visually consistent. Individual game pages are free to look however they want — no imposed styling once you're inside a game.
- **Cadence:** something new or updated must become visible on the site at least once every 2 weeks. Not every-game-every-week — just *something*.
- **Scope philosophy:** let each game be as big or small as the idea wants. The bar is "visible and real," not "polished/finished." Don't let polish-chasing block shipping.
- **Reviews/ratings:** star rating + comments per game is the public-feedback mechanism for both subjects. Live and persistent: hub's review widget calls the `/app` FastAPI backend (deployed on FastAPI Cloud, Neon Postgres) — see `planning/pwa-and-ads-setup.md` and `app/main.py`.

## Session logging (do this every session, before ending)
Two running logs live at the repo root: `BCM206-DEV-LOG.md` (site infrastructure — hosting, save system, accounts, deployment, backend) and `BCM114-DEV-LOG.md` (individual game content — mechanics, style, narrative, GenAI prompt iteration).

Before ending any session where code or content changed, append one dated entry to whichever log(s) apply — split across both if the session touched both. Follow the entry format already defined inside each log file. Append only — never edit or remove a past entry. If nothing meaningfully changed, skip logging rather than writing a filler entry.

**Also check off any completed items in `planning/TODO.md`** as they land — it's the standing cross-game/site task list, meant to replace tracking work purely through scattered planning docs. Don't create a new planning `.md` for a cross-cutting idea or gap; add it to `TODO.md` (or `LATER.md` if it's genuinely parked) instead. **Whenever you check off one or more items, also recompute and update the "Progress: X/Y" line at the top of `TODO.md`** — `grep -c "^\s*- \[[ x]\]" planning/TODO.md` for the total, the same with `\[x\]` for the done count.

**Read `planning/AI-COORDINATION.md` at the start of every session, before any work.** The two Claude sessions (Noy2, Noyvj) never run at the same time, but a session-limit cutoff can leave the other one's work (or a background agent) half-finished; that board's "In progress" lines say what to leave alone or finish. Edit it before starting or switching work, and keep it current.

**Check `planning/FOR-YOU.md` at the start of every session.** It holds action items only the user can do (an external account signup, a production deploy needing their own login) and open questions only they can answer. If they've filled in an answer or told you an action item is done, act on it, fold the result into the relevant doc/commit, then remove that entry from the file. Add a new entry there — rather than asking the user directly and losing the question when the session ends — whenever you hit a decision that's genuinely theirs to make, or a step that genuinely needs their own credentials/account.

**Archiving a completed `planning/TODO.md`.** Once every item in the current `TODO.md` is checked off (or it's otherwise being retired for a fresh one), move the file into `planning/todo-archive/` — gitignored, local-only, not part of this repo's git history (unlike `planning/archive/`, which deliberately keeps resolved *design* docs in git for BCM206 process-evidence; a fully-checked task list doesn't carry that same evidentiary value). Rename it `YYMMDD_YYMMDD.md`: the first date is when that list was created (check `git log --follow --diff-filter=A -- planning/TODO.md`, or the date on its own first commit if it's a fresh file), the second is the day it's archived. Then start a fresh `planning/TODO.md` for whatever comes next.

## Per-game conventions (apply inside every `/games/<slug>/`)
- Default stack: Python via Pyodide, plain HTML/CSS, no build step. Deviating (e.g. plain JS for something trivial) is a deliberate documented exception, not a default.
- Each game keeps its own `CLAUDE.md` with concept, constraints, and a numbered milestone table — same format as SOL's.
- Commit + tag per milestone: `git commit -m "Milestone N: <name>"` then `git tag <game-slug>-milestone-0N`.
- Update each game's milestone Status column as work happens, so context here always reflects real state.

## Working notes
- Z30 favicon fix (2026-09-21): every game's `index.html` (and the hub's own root `index.html`) pointed its `<link rel="icon">` at the exact same `icons/icon-192.png` — a player with several NoyvjGames tabs open had zero way to tell them apart by favicon. Gave each of the 12 games its own distinct `icons/favicon-<slug>.svg` (rounded-square background in that game's own established hub-thumbnail accent color — the same `--thumb-glow`/gradient values `style.css`'s `.title-card-thumb--*` classes already define per game — with a single bold white letter or a small glyph centered: leaf for Canopy, bolt for Grid, double-wave for Tide, snowflake for Thaw, infinity for Loop, gold `$` on navy for Trade Empire, violet-to-amber gradient + "C" for Continuum, green field + "F" for Le Champ de Mots, plain bold initial for SOL/Aftermath/Herd/Drift). Same shape/frame convention across all 12 so they read as one site's games, not unrelated icons. `icons/icon-192.png`/`icon-512.png` untouched — confirmed `manifest.json` only references those two for PWA install, unrelated to the per-page browser-tab favicon. The hub's own root `index.html` deliberately kept the original placeholder icon (it's the "home" of the site, per the task's own framing). Verified live via the shared `hub-dev-server`: SOL/Canopy/Continuum/Le Champ de Mots each fetch their own new SVG with a 200 and `image/svg+xml` content-type, and a side-by-side render of all 12 at both 64px and 16px confirmed every glyph stays legible and visually distinct even shrunk to browser-tab size.
- Colorblind-safety audit, hub shell (`planning/TODO.md`'s site-wide goal, A10/L5) — audited, no change needed. Checked every place the root shell conveys state: the star-rating widget (`.star`/`.star.selected` in `style.css`), the achievements-dashboard progress bars (`.achievements-bar-fill`), sign-in/sign-up status text (`#account-status`), the review-widget and site-feedback submit success/failure states, and `script.js` for any inline JS-set colors. Found no hue-only encoding anywhere: every success/error/status message on the hub shell (sign-in failure, submit failed, "reviews unavailable," etc.) is plain text with no color differentiation at all — success and failure share the exact same `.account-status`/button styling, so there's nothing to confuse. The achievements bars are a single-hue blue gradient (`#6f8fe0`→`#a9c3ff`), not paired against a contrasting "bad" color, same "single-hue bar" case Continuum's own audit ruled out. The star widget's selected/unselected states (`#e0c24c` gold vs. `#3a3f52` dark slate) are a large lightness/luminance jump, not the red/green or blue/purple hue-only pairs deuteranopia/protanopia/tritanopia actually confuse. No red/green pair exists anywhere in `style.css` or `ad-bar.css`. Same "no change needed" conclusion as Tide's D11, verified live via the shared `hub-dev-server` (sign-in, sign-out, invalid-login, and star-click all confirmed working with zero console errors).
