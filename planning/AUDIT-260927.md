## D. Live playtest — per-game (mobile width, 375px, real pointer clicks)

Ran every one of the 13 hub games at 375px: navigate, wait for boot, check console

overflow, on all 13:** SOL, Canopy, Grid, Tide, Aftermath, Herd, Thaw, Loop, Drift,

### D1. [P1] Signal: tutorial auto-starts over the still-open "New Game" screen
On a completely fresh visit to Signal (no `tutorial-seen:signal`, no save), the
onboarding tutorial's full-screen spotlight overlay (`#tutorial-overlay`, z-index
10000) appears immediately — but the game's own opening screen ("New Game / Saves /
Settings / Info / Feedback") is what's actually still showing underneath it. The
tutorial's step 1 says "Tap a tile to ping it," but there is no tile to tap yet — the
spotlight cutout just frames the opening screen's own buttons. Confirmed live: a real
pointer click at the exact reported location of grid tile A1 hits an invisible
`<div id="tutorial-overlay">` sitting on top of everything, not the tile.

**Root cause, found by reading the code:** `shared/opening-screen.js` sets
`window.__openingScreenOwnsTutorial = true` (unconditionally, every game)
specifically so `shared/tutorial.js`'s `GameTutorial.init()` skips its own auto-start
and lets the opening screen offer the tutorial from its own "New Game" step instead.
That check happens synchronously, at the moment `init()` is called. In every one of
the other 12 games, the `GameTutorial.init()` call sits inside an `async function
main()` that only runs after `await pyodide.runPythonAsync(code)` — i.e. after the
whole Pyodide engine has booted (1-4+ seconds) — by which time `opening-screen.js`'s
plain synchronous `<script src>` tag (which appears later in the HTML but loads in
milliseconds) has already run and set the flag. **Signal has no Pyodide-dependent
engine wait** — its `GameTutorial.init(...)` call sits in a plain top-level
`<script>` block, deliberately "wired up right away (no engine needed)" per its own
comment — so it runs during initial page parse, before the browser even reaches the
later `<script src="../../shared/opening-screen.js">` tag. The flag isn't set yet,
the `!window.__openingScreenOwnsTutorial` check reads truthy, and the tutorial
auto-starts exactly the way it would for a game with no opening screen at all.

Verified this is Signal-specific, not systemic: checked all 13 games'
`GameTutorial.init` vs `opening-screen.js` script-tag order — the raw HTML order has
`init` textually before `opening-screen.js` in **all 13** (would look like a
site-wide bug from a text search alone), but for every other game that call is
inside the Pyodide-boot `async main()`, so it *actually executes* after
`opening-screen.js` has already run. Signal is the only game whose tutorial wiring
runs synchronously at parse time, so it's the only one where the textual order and
the real execution order match — and that's exactly the case that breaks.
**Fix needed:** move Signal's `<script src="../../shared/opening-screen.js">` (and
ideally `save-widget.js`/`hub-auth.js`, same reasoning) above the inline `<script>`
block that calls `GameTutorial.init()`, or delay that call with the same
`window.setTimeout`/promise pattern the opening screen's own `choice` promise offers.

### D2. [P2] Opening screen shows "New Game" instead of "Continue"
Found while testing Continuum's new "Found a New Settlement" button. With a
Continuum tab that clearly has real progress (1/21 achievements, an active
Tribal-era settlement, all visible directly once the opening screen is dismissed),
reloading the page consistently shows `shared/opening-screen.js`'s screen with
**"New Game" as the primary button and "Continue" hidden**. Read (didn't execute
further — didn't want to risk the one settlement I was using as a live test subject)
`shared/opening-screen.js`: `hasSave()` is `signedIn() || Boolean(storedCode())` — it
only recognizes the shared account/save-code system, not a game's own always-on
local autosave. Since I never clicked "Save Progress" to mint a code, `hasSave()` is
false regardless of how much real local progress the engine has, so a returning
player who relies purely on autosave (never grabbed a save code, never signed in)
sees "New Game" front and center. Reading `askNewGame()` further: when there's no
stored code, clicking "New Game" calls `go()` with **no confirmation dialog at all**
(the `ConfirmDialog` branch is gated on `code && window.ConfirmDialog`), and `go()`
never touches the engine's own local-autosave key — it only resolves a promise
`save-widget.js` uses to skip its *account*-based autoload. So my best reading is
that clicking "New Game" here would NOT actually erase the local autosave (the
engine likely already loaded it before the opening screen even finished deciding
what to show) — but I did not click it to verify, since if that reading is wrong it
would erase real test state with no undo. **This needs a deliberate, disposable-
profile test** (click "New Game" on a game with known local-only progress and
confirm afterward whether that progress survived), not more speculation from me. If
local progress *does* survive, the only real issue is the button being labeled
misleadingly (there's no confirm step to reassure a cautious player); if it does
NOT survive, this is a real, unguarded data-loss button for any player who never
made a save code.

## E. Live playtest — Warframe Build Tracker (not hub-linked, but part of the repo)

### E1. [P1] "Sign Out" always shows, even signed out
Loaded `warframe_build_tracker/index.html` signed out (no bearer token in
`localStorage`). It correctly shows "Sign In" / "Create Account" — but a "Sign Out"
button is ALSO visible at the same time, right next to them. Confirmed the cause:
`#account-signed-in` has `hidden` set correctly by the JS (`hiddenAttr: true`), but
`warframe_build_tracker/style.css` (around line 95) defines
`#account-signed-in { display: flex; ... }` unconditionally, with no matching
`#account-signed-in[hidden] { display: none !important; }` override anywhere in the
file — so the CSS's own `display: flex` wins over the browser's default
`[hidden] { display: none }` rule, and the "signed in" block (an empty username line
plus "Sign Out") renders regardless of sign-in state. This is the exact same class of
bug as `shared/confirm-dialog.js`'s skip-row issue found and fixed earlier today (a
`display` rule beating `[hidden]`), just in a different file that fix didn't touch.
The hub's own root `style.css` has no such override for `#account-signed-in`
(confirmed by grep — only a comment mentions the id, no rule), so the hub itself is
fine; this is scoped to the Warframe tracker's own stylesheet. None of the 13 hub
games define their own `#account-signed-in` at all. **Fix:** add
`#account-signed-in[hidden] { display: none !important; }` to
`warframe_build_tracker/style.css`, same pattern as today's confirm-dialog fix.
Batch-B's new "Deeper planners" tab strip (10 tabs) switched cleanly with no console
errors during a spot check.
