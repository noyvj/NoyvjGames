Fixed with a `JSON.stringify` replacer mapping `undefined` back to `null`, in the one shared widget file — fixes every game at once, no per-game changes needed. The clearest cross-cutting infra lesson from this pass: three separate games' audits (SOL, Aftermath, and — in a non-coursework game — Continuum) independently found the same *class* of save-system bug: a save/load path that works for "same build, same session" but silently corrupts or crashes on "load a save written by an older or newer build than the one currently running" (a wholesale dict-replace stomping keys the current build expects but an older save doesn't carry, or vice versa). None of the per-game save code shares an implementation — each game owns its own `get_state()`/`load_state()` — so this wasn't one shared bug, but the same failure shape recurring three times independently is worth remembering as a standing risk of the save widget's "opaque dict" contract: every game's own save code needs to merge/guard defensively against a save written by a different version of itself, not just trust its own current shape.
**Result:** All 12 games' test suites plus the backend suite pass with zero regressions: 1,803 game tests + 40 backend tests. Working tree clean, 16 audit commits total (one per game that had something to fix, plus the root-level fixes and the title-consistency pass). ### 2026-09-02 (continued further)
**Touched:** one commit per game (see below); no further root-level files
**Did:** The user pushed back on the audit above being too conservative — "there were a lot of non-urgent but concerning flags... go again and just do anything you notice whether it is urgent or not" — so ran a second, explicitly more-aggressive pass, one parallel agent per game again, each told to actually fix (not just flag) two specific patterns found earlier: (1) a Pyodide `create_proxy()` call inside any function that reruns every repaint, never `.destroy()`d — a slow per-session memory leak; (2) any other instance of the save-merge bug (a wholesale dict-replace on load instead of a key-by-key merge). Aftermath also turned up a second-order bug in its own first-pass fix: the new-run counter derived its number from a possibly-stale reloaded run rather than the high-water mark, so a genuinely new run could silently collide with an already-awarded run number and pay out nothing.
**Result:** All 12 game suites + backend suite green (final counts below), zero regressions, one commit per game with something to fix (Trade Empire came back clean — it has no save system yet, so the merge bug doesn't apply there). Revised lesson from the entry above: "merge, don't replace" and "destroy proxies you create in a re-run function" are now confirmed as genuinely hub-wide risks worth checking by default on any future game, not edge cases — likely because every game's save/render code was written independently against the same shared-widget "opaque dict" contract and Pyodide's proxy-lifetime rules, so the same mistake gets made independently each time rather than copy-pasted. Worth adding a short note to `planning/SAVE-BUTTON-INTEGRATION.md` and a future game-template checklist reminding of both patterns up front, rather than relying on audits to catch them after the fact.
