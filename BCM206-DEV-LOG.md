### 2026-08-15
**Touched:** `app/models.py`, `app/main.py`, `app/tests/test_save_system.py`, `games/sol/game.py`, `games/sol/tests/test_save_system.py`, `games/sol/index.html`, `games/sol/style.css`, `planning/SAVE-SYSTEM-DESIGN.md`
**Did:** Built Phase 1 of the save system from `SAVE-SYSTEM-DESIGN.md` — save codes, no accounts. Added a `Save` model (SQLAlchemy, `saves` table) and three endpoints (`POST /saves`, `GET /saves/{save_code}`, `PUT /saves/{save_code}`) to the FastAPI backend, with unambiguous-alphabet code generation (`XXXX-XXXX`, excludes `0/O/1/I/L`) and collision retry on insert. Wired SOL up as the reference integration: `serialize_state()`/`deserialize_state()`/`get_save_state_json()`/`load_save_state_json()` in `game.py`, plus a documented plain-JS bridge in `index.html` (Save/Load buttons, localStorage-remembered save code) that fetches the deployed API. Two deliberate deviations from the original spec, both for sqlite-test-suite portability: `id` is a Python `uuid.uuid4()` string instead of Postgres `gen_random_uuid()`, and `save_data` uses generic SQLAlchemy `JSON` instead of `JSONB`.
**Result:** 9 new backend tests + 8 new SOL tests, all passing (490 total across the site, 0 regressions). Caught and fixed a real bug via the test suite: `serialize_state()` was returning a live reference to `planet_state` instead of a deep copy, so post-save mutation could corrupt the "saved" snapshot — fixed with `copy.deepcopy()`. Verified live end-to-end against a temporary local backend instance (save → code → fresh page load → load by code → state restored, including mid-travel state), then reverted the API URL back to production before committing. Other games can adopt the same bridge pattern later; Phase 2 (accounts) is still just a design, not started.

Feedback submission gets a simple in-process per-IP rate limit (5/hour) per the doc's own "keep it minimal" moderation guidance.
**Result:** 21 new backend tests (11 accounts, 10 feedback), 36 total in `app/`, all passing, zero regressions. No frontend wired up yet — no sign-in UI, no feedback widget on the hub or any game page, and SOL's existing save UI doesn't yet offer to claim a save. That's the natural next step whenever it's wanted.

### 2026-08-19 (revised same day)
**Touched:** `app/models.py`, `app/main.py`, `app/tests/test_accounts.py`, `app/tests/test_feedback.py`, `index.html`, `style.css`, `script.js`, `planning/ACCOUNTS-AND-FEEDBACK-DESIGN.md`
**Did:** Replaced the just-built magic-link/email auth with username + password, per feedback that email was too much infrastructure for a second-pass update and a preference for no password-complexity rules. Removed `AuthToken`/stub mode/`/auth/request-link`/`/auth/verify` entirely; `User.email` became `User.username` (stored lowercased, normalized on every read/write so case can't create lookalike duplicates) plus a new `password_hash` column. Passwords are hashed with salted PBKDF2-HMAC-SHA256 (600k iterations, stdlib `hashlib`/`os`/`secrets` only — no new dependency) via `_hash_password`/`_verify_password` in `main.py`; no strength policy is enforced server-side, matching what was asked for. New endpoints `POST /auth/signup` and `POST /auth/login` both return a bearer token immediately (sign-up logs you in, no separate step). The `AuthSession` bearer-token table needed no changes — it never cared how identity was proven. Hub UI swapped the stub-token box for username/password fields and two buttons (Sign In / Create Account), with an advisory (non-blocking) password hint about there being no reset path yet. SOL's claim button was untouched — it only ever checked for a bearer token in `localStorage`, indifferent to how it got there.
**Result:** 40 backend tests (was 36 — accounts tests rewritten for signup/login, feedback's one auth-dependent test updated), all passing. Verified end-to-end in-browser again against a fresh local backend: signed up, signed out, signed back in with the same credentials, confirmed a wrong password is rejected with "Invalid username or password," then repeated the SOL save → claim → hub "My saves" flow from the session above with the new auth — all working identically. Production API URL reverted before finishing, same pattern as before; still not deployed. Explicitly flagging one real tradeoff, not just a code note: with no email on file, there is no way to recover a forgotten password — that account's claimed saves/feedback become permanently stranded. Deferred, not solved, until email accounts are worth the setup.

### 2026-08-20
**Touched:** none directly — process note about the 8-game Pass 3 build logged in `BCM114-DEV-LOG.md` today (game-content side of that session)
**Did:** Ran Iteration Pass 3 (fun/teaching-balance fixes) across all 8 climate games as 8 fully parallel agent sessions, since each game's fix was self-contained within its own directory. Two of them (Canopy and Tide) ran `git add`/`git commit` close enough together to race on the shared `.git/index` in this single working tree — Tide's agent staged its finished files, Canopy's agent's `git commit` (which commits the whole index, not just the paths it explicitly passed) swept them in too, so both games' Pass 3 work ended up in one commit (`755bc1f`) carrying only Canopy's message. Confirmed via `git diff` that this is cosmetic, not corruption: both games' files are present, complete, and correctly isolated (no cross-game contamination), and every affected game's test suite passes. Attempted to split it into two clean commits via a local interactive rebase (safe in principle — all 7 Pass 3 commits are unpushed, 7 commits ahead of `origin/main`, so no shared history would be disturbed) but the harness's auto-mode safety classifier blocked the rebase outright as a git-history-rewrite action, regardless of context. Did not attempt to work around that block.
**Result:** All 8 games' Pass 3 work is committed and correct; 834 tests passing site-wide, zero regressions. One commit (`755bc1f`) has a misleading message (says "Canopy," contains Canopy + Tide) — flagged to the user directly rather than silently left implicit; a manual `git rebase -i` (or accepting it as-is) is the user's call to make, not something to route around a safety block for. Lesson for future multi-agent sessions touching git: either serialize commit steps across parallel agents, or give each agent its own worktree, to avoid this race entirely.

### 2026-08-20 (continued)
**Touched:** `shared/save-widget.js` (new), `planning/SAVE-BUTTON-INTEGRATION.md` (new, copied from an external draft), root `index.html`, root `CLAUDE.md`, `games/sol/{game.py,index.html,style.css,tests/test_save_system.py}`, plus one commit per climate game (`games/{grid,canopy,tide,aftermath,herd,thaw,loop,drift}/{game.py,index.html,tests/*}`)
**Did:** Built `SAVE-BUTTON-INTEGRATION.md`'s shared save widget and rolled it out to every game in the hub. One script (`shared/save-widget.js`) renders a small fixed-position Save/Load UI and talks to the existing `/saves` API; the per-game contract is just two Python functions (`get_state()`/`load_state(data)`) plus `window.pyodide = pyodide;` in the boot script. Built and proved it against SOL first (migrating off its bespoke save/load bridge from the Phase 1 session, onto the shared widget — same dict shape via thin wrappers around the existing `serialize_state`/`deserialize_state`, so old save codes still load), then rolled it out to all 8 climate games as 8 parallel agent sessions, each reading its own `game.py` to determine the real state shape and writing its own round-trip tests. Learned from the Pass 3 git-index race: every agent was told to stage and commit via explicit pathspec only (`git add <exact files>` / `git commit -m "..." -- <same files>`, never a bare `git add .`/`git commit`) — this time all 8 landed as clean, individually-attributed commits with zero cross-game contamination.

Caught a real bug during my own pre-rollout verification of the widget (not by any of the per-game agents, since none of them tested live in-browser save/load against a running backend — only pytest): Pyodide's `PyProxy.toJs()` converts a Python `None` to JS `undefined`, and `JSON.stringify` silently drops any object key whose value is `undefined`. Every nullable field a game tracks (e.g. Grid's `last_event`/`last_aging_event`, `None` until the first one fires) was vanishing from every save — confirmed via a live save/load round trip against a local backend, where a fetched save's `last_event` key was entirely absent rather than `null`. Fixed with a `JSON.stringify` replacer mapping `undefined` back to `null`, in the one shared widget file — fixes every game at once, no per-game changes needed. Re-verified the same round trip afterward: field present, save/diverge/load restores the exact saved round number.

Also fixed a second, separate, previously-undiscovered production bug, found while working out the widget's own relative include path: every absolute root-relative path across the *entire site* (favicon, `ad-bar.css`, `manifest.json`, service-worker registration, every game's hub-back-link) 404s on the live site, because GitHub Pages serves this repo under `/NoyvjGames/`, not the domain root — confirmed live (`https://noyvj.github.io/manifest.json` 404s; `https://noyvj.github.io/NoyvjGames/manifest.json` works). This had been broken since the 2026-08-18 favicon/back-link session and was never caught because all verification up to that point ran against a local server (which serves the repo at its own root, masking the bug) rather than the true production subpath. Fixed in every touched file this session (root `index.html`, SOL, all 8 climate games) by converting to `../../`-relative paths; **Trade Empire and Continuum's own pages were not touched here** since they're not yet hub-linked — same bug likely applies there once they are, worth a pass before either goes live.
**Result:** 1,471 game tests (across SOL, all 8 climate games, and Continuum) + 40 backend tests passing site-wide, zero regressions. Verified live in-browser (local backend) on SOL and Grid: real save codes generated, full field-set round trips including previously-buggy nullable fields, load correctly reverts diverged state. Both the shared-widget rollout and the path-bug fix are committed but **not yet deployed/pushed** — same status as the accounts/feedback work from the previous entry.
